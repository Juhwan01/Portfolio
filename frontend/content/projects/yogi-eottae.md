## 구조 결정

### 1. 추천 점수: 리뷰 평가 + 이동 부담

**왜:** 외국인 관광객에게는 한글 중심 버스 시스템과 복잡한 환승 구조가 가장 큰 장벽입니다. 평점이 높아도 캐리어를 끌고 언덕을 넘어야 한다면 의미가 없고, 걸어서 다니는 여행객은 총 시간이 10분 늘어나는 것보다 환승이 1회 늘어나는 것을 훨씬 피곤해합니다.

**구조:** 도보 거리, 환승 횟수, 이동 시간을 이동 부담 점수로 묶고, 도보와 환승에 시간보다 큰 비중을 뒀습니다. 벡터 검색이 고른 후보를 이 이동 점수와 리뷰에서 뽑은 외국인 친화도·품질, 가격대가 맞는지로 다시 매겨 상위 10곳을 추천합니다.

### 2. 경로 계산: 그래프 DB 대신 자체 대중교통 라우팅 서버

**왜:** 이동 마찰을 후보마다 실시간으로 계산하려면 대중교통 경로를 직접 계산해야 했습니다. 처음 시도한 그래프 DB(Neo4j)는 배차·환승 같은 시간표 데이터를 다루지 못했습니다.

**바꾼 구조:** GTFS 데이터에서 오류를 내던 34만 건을 정제해 GraphHopper 라우팅 서버를 직접 띄우고, 벡터 검색이 고른 후보 50곳의 경로를 `asyncio.gather`로 동시에 계산합니다.

**결과:** 대한민국 전역의 대중교통 경로를 계산하는 라우팅 서버를 RAG 추천과 하나의 파이프라인으로 묶었습니다.

### 3. 추천 흐름: 멀티 에이전트 대신 단일 RAG 파이프라인

**왜:** 처음 설계한 LangGraph 멀티 에이전트는 맛집 추천에는 필요 이상이었습니다. 필요한 건 "혼밥하기 좋은 분위기 있는 파스타집" 같은 자연어의 뜻을 잡고, 새 식당 데이터가 들어와도 다시 학습하지 않는 추천이었습니다.

**바꾼 구조:** LLM과의 대화로 13가지 항목의 프로필을 받고, ChromaDB 벡터 검색으로 후보를 찾는 하나의 흐름으로 줄였습니다.

**결과:** 구조를 줄인 만큼 위치 기반 추천에 집중했습니다.
