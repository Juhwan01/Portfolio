## Problem

외국인 관광객을 위한 맛집 추천 서비스는 많지만, **"좋은 식당"과 "갈 수 있는 식당"은 다릅니다.**

> 리뷰 1,000개의 5점짜리 맛집도, 캐리어를 끌고 언덕을 넘어야 한다면 무의미한 숫자에 불과합니다.

한글 중심 버스 시스템, 복잡한 환승 구조 속에서 뚜벅이 여행객에게는 **이동 편의성이 추천의 핵심 변수**여야 합니다. 우리의 질문은 "어디가 유명한가?"가 아니라, **"당신에게 지금 가장 완벽한 곳은 어디인가?"**였습니다.

## My Role: AI Lead (팀장)

4인 AI 팀의 **팀장**으로 RAG 추천 파이프라인 설계, GraphHopper 라우팅 엔진 구축, 데이터 수집/전처리를 주도했습니다.

| 담당 영역 | 구현 내용 |
|-----------|----------|
| RAG 파이프라인 | ChromaDB 벡터 검색 + LLM 추천 로직 설계 |
| 라우팅 엔진 | GraphHopper 자체 서버 구축, GTFS 34만 건 클렌징 |

| 인프라 | Docker Compose 멀티 컨테이너 배포 |

## Approach

### 1. 왜 RAG인가?

사용자는 "혼밥하기 좋은 분위기 있는 파스타집"처럼 자연어로 질의합니다.

| 방식 | 자연어 이해 | 맥락 파악 | 새 데이터 반영 |
|------|-----------|----------|--------------|
| 키워드 검색 | X | X | 즉시 |
| 추천 알고리즘 | X | 제한적 | 재학습 필요 |
| **RAG** | **O** | **O** | **즉시** |

LLM으로 13가지 항목의 대화형 프로필을 수집하고, **ChromaDB 벡터 검색**으로 7,700개 식당 데이터와 연결했습니다.

### 2. 이동 편의성을 어떻게 정량화할 것인가?

뚜벅이 여행객은 "총 시간 10분 증가"보다 "환승 1회 추가"에 훨씬 큰 피로를 느낍니다. 이 저항을 **이동 마찰 점수**로 정의했습니다:

> **이동 마찰 = 도보(0.4) + 환승(0.4) + 시간(0.2)**

이 점수를 실시간으로 계산하려면 자체 라우팅 엔진이 필요했습니다.

### 3. 라우팅 엔진: 3번의 도전

| 시도 | 엔진 | 결과 | 원인 |
|------|------|------|------|
| 1차 | Neo4j | 실패 | 배차/환승 등 시간 데이터 처리 불가 |
| 2차 | OTP | 실패 | 34만 건 유령 오류, Python 검증은 "정상" |
| **3차** | **GraphHopper** | **성공** | Java 오류 로그에서 범인 발견 |

GTFS 데이터의 `stop_sequence` 필드가 `2.000000000`(실수형)으로 저장되어, Python은 너그럽게 통과시켰지만 Java는 거부했습니다. 34만 건 데이터 클렌징 후 대한민국 전역의 대중교통 라우팅이 가능한 **자체 서버 구축에 성공**했습니다.

### 4. 최종 추천 파이프라인

```
[사용자 질의]
  -> ChromaDB 벡터 검색 (후보 50개)
  -> GraphHopper 비동기 50개 경로 동시 계산 (asyncio.gather)
  -> 최종 점수 = 유사도(0.6) + 이동 편의성(0.3) + 평점(0.1)
  -> 상위 10개 추천
```

데이터는 7,700개 가게 리뷰를 수집하고, 표준/한글/영어 3단계 매칭으로 **94.57%**(6,842개) 매핑에 성공했습니다.

## Results

- 자연어 질의 기반 위치 인식 맛집 추천 시스템 **프로덕션 배포**
- RAG + 자체 GraphHopper 라우팅 엔진 통합
- 7,700개 가게 중 **94.57% 데이터 매핑** 성공
- **kakao x goorm 부트캠프 우수프로젝트상 수상**

## Lessons Learned

> 기술 선택은 "무엇이 최신인가"가 아니라 "무엇이 이 문제에 적합한가"로 결정해야 합니다.

처음에는 LangGraph 멀티 에이전트 구조를 설계했지만, 맛집 추천은 단일 RAG 파이프라인으로 충분했습니다. 오버엔지니어링을 줄이고 **핵심 가치(위치 기반 추천)**에 집중한 것이 수상의 결정적 요인이었습니다.
