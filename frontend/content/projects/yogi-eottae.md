## 맥락과 제약

- **좋은 식당과 갈 수 있는 식당은 다릅니다:** 외국인 관광객용 맛집 추천은 많지만, 평점이 높은 식당도 캐리어를 끌고 언덕을 넘어야 한다면 의미가 없습니다.
- **대중교통이 가장 큰 장벽:** 한글 중심 버스 시스템과 복잡한 환승 구조 때문에, 걸어서 다니는 여행객에게는 이동 편의성이 추천의 핵심 변수여야 했습니다.
- **질문은 자연어로 들어옵니다:** "혼밥하기 좋은 분위기 있는 파스타집"처럼 묻기 때문에, 키워드가 아니라 뜻과 맥락을 잡아야 합니다.

## 핵심 결정

1. **추천은 RAG로 한다.** 키워드 검색은 자연어와 맥락을 이해하지 못하고, 일반 추천 알고리즘은 새 데이터를 반영하려면 다시 학습해야 합니다. LLM과의 대화로 13가지 항목의 프로필을 받고, ChromaDB 벡터 검색으로 맞는 식당 후보를 찾습니다.
2. **이동 부담을 점수로 만든다.** 걸어서 다니는 여행객은 총 시간이 10분 늘어나는 것보다 환승이 1회 늘어나는 것을 훨씬 피곤해합니다. 그래서 이동 마찰을 도보(0.4) + 환승(0.4) + 시간(0.2)으로 정의하고, 최종 점수를 유사도(0.6) + 이동 편의성(0.3) + 평점(0.1)으로 매겨 상위 10곳을 추천합니다.
3. **대중교통 라우팅 서버를 직접 띄운다.** 이 점수를 실시간으로 계산하려면 자체 라우팅 엔진이 필요했습니다. GTFS 데이터로 GraphHopper 서버를 구축하고, 벡터 검색이 고른 후보 50곳의 경로를 `asyncio.gather`로 동시에 계산합니다.

## 막혔던 것

- **Neo4j로는 시간표를 다룰 수 없었습니다:** 그래프 DB로 경로를 찾으려 했지만 배차·환승 같은 시간 데이터를 처리하지 못해 접었습니다.
- **OTP(OpenTripPlanner)의 34만 건 유령 오류:** 오류가 34만 건 났는데 Python 검증으로는 데이터가 "정상"이었습니다. GraphHopper로 옮긴 뒤 Java 오류 로그에서 원인을 찾았습니다. GTFS의 `stop_sequence`가 `2.000000000` 같은 실수형으로 저장돼 있어 Python은 통과시키고 Java는 거부한 것입니다. 34만 건을 정제한 뒤에야 라우팅 서버가 돌았습니다.
- **처음 설계한 멀티 에이전트 구조:** LangGraph 멀티 에이전트로 설계를 시작했지만 맛집 추천은 단일 RAG 파이프라인으로 충분했습니다. 구조를 줄이고 위치 기반 추천에 집중했습니다.
