2026년 9월 13일 베타를 열었고, 베타 중에 Google Play(9월 21일)와 App Store(9월 25일)에 정식 출시했습니다. 위의 베타 수치는 9월 13일부터 30일까지 잰 값입니다.

## 구조 결정

### 1. 일반 대화: 여러 경로 대신 모델 하나·경로 하나

**왜:** 일반 대화가 지식 베이스 검색, 도구 호출 판단, 가벼운 질문용 경로, 상위 모델로 넘기는 경로까지 여러 경로로 나뉘어 있었습니다. 그중 한 경로에서는 같은 앞부분을 다시 계산하지 않게 해 주는 프롬프트 캐시가 13번 호출 중 한 번도 적중하지 않았습니다. 매 대답 앞에서 요청을 분류하는 AI 호출(이하 판단기)도 응답 시간 중앙값이 9.5~15.7초였습니다.

**검증:** 지식 베이스를 빼기 전에 따로 떼어 둔 200문항으로 시험했습니다. 지식 베이스 없이 모델이 혼자 답해도 99.0%가 사실 검사를 통과했습니다. 반면 지식 베이스 안에 답이 있던 문항은 90.0%에 그쳤습니다.

**바꾼 구조:** 이 경로들을 모두 걷어내고 모델 하나와 호출 경로 하나로 합쳤습니다. 판단기도 같은 모델로 바꾸고 추론 단계를 껐습니다.

**결과:** 2026년 8월 서버에 배포한 뒤 시험 대화 5턴에서, 프롬프트 캐시가 판단기는 2턴째, 응답 모델은 3턴째부터 계속 적중했습니다. 판단기 응답 시간 중앙값은 1.3~1.8초로 줄었습니다. 운영 서버에서도 베타 기간(9.13–9.30) 채팅 입력 토큰의 58%를 캐시에서 읽었습니다.

### 2. 기록 변경: 한 번에 다 정하던 AI 호출 대신 단계별 루프

**왜:** 대화로 운동·식단 기록을 바꿀 때, AI 호출 한 번이 무엇을 바꿀지와 어떤 값을 넣을지, 더 할 일이 있는지까지 한꺼번에 정했습니다. 그래서 추천받은 루틴을 "넣어줘"라고 하면, 회원 승인을 받는 확인 창에 종목 일부만 담기는 일이 같은 사례 10번 중 9번 생겼습니다.

**바꾼 구조:** 요청마다 분류 → 실행 → 검사 → 응답을 차례로 도는 루프로 바꾸고, 부탁마다 반영됐는지 코드가 끝까지 확인해 말없이 빠지는 부탁이 없게 했습니다. 이어서 기록 변경 요청에서는 기록 조회 단계를 건너뛰게 해 느린 응답을 줄였습니다.

**검증과 결과(개발 환경):**
- 같은 실패 사례 10번 재현: 확인 창에 일부만 담기는 일이 9번에서 0번으로 줄었습니다.
- 46개 상황으로 돌린 대화 232건 가운데 228건이 끝까지 반영됐습니다.
- 기록 조회 단계를 건너뛴 뒤, 전에는 기록 조회까지 함께 돌던 대답의 느린 쪽 10%(p90) 응답 시간이 33.1초에서 16.0초로 줄었습니다.

**반영:** 개발 브랜치에서 이 구조로 전면 교체했고, 운영 배포 전 시험을 이어 가고 있습니다.

### 3. 대답 앞 판단: 분류용 AI 호출 대신 결정 모델

**왜:** 판단기 하나가 요청 분류, 회원 정보 추출, 기록 조회 SQL 작성까지 한 호출에서 했습니다. 이 호출이 끝나야 답을 쓰기 시작할 수 있었고, 분류가 틀려도 어디서 틀렸는지 찾기 어려웠습니다.

**바꾼 구조:** 분류는 결정 모델(OpenAI Decisions API)에 맡겼습니다. 결정 모델은 글을 쓰지 않고, "기록을 바꿔 달라는 말인가" 같은 질문 13개에 예/아니오 확률이나 고른 보기만 돌려줍니다. 확률이 기준값을 넘는지 보고 다음 단계는 코드가 정합니다.

**검증(개발 환경):** 같은 코칭 대화 12턴 대본을 바꾸기 전 서버와 바꾼 서버에 넣어 비교했습니다. 처음에는 같은 뜻의 말에도 확률이 크게 갈려서("지워줄래?" 1.00, "빼주세요" 0.23), 질문마다 정답 세트를 만들어 질문 문장과 기준값을 다시 골랐습니다.

**결과:** 답을 쓰기 전 판단 시간이 2.65초에서 0.40초로 줄었습니다(기록 조회 없는 8턴의 중앙값). 대답 전체 시간 중앙값은 10.55초에서 9.39초가 됐고, 대답 한 번의 평균 비용은 거의 그대로(−3.4%)였습니다. 확인 창에 "응", "아니"로 답한 것을 읽는 승인 판정은 결정 모델의 정확도가 88.9%로 지금 방식(93.7%)보다 낮아 옮기지 않았습니다.

**반영:** 개발 브랜치에서 판단기를 걷어내고 전면 교체했습니다. 운영 배포 전입니다.

### 4. 월간 리포트: 실시간 호출 대신 Batch API

**왜:** 매달 1일 대상 회원 전원의 종합 리포트는 하루 안에만 끝나면 되는 작업이라, 결과가 늦게 오는 대신 단가가 절반인 Batch API를 골랐습니다.

**구조:** Batch API는 결과가 최대 24시간 뒤에 오는데, 작업을 돌리는 Lambda 하나는 15분까지만 돌아갑니다. 그래서 AWS Step Functions로 Lambda 여섯 개를 이어 긴 기다림을 나눠 맡게 했습니다. 요청 제출, 10분 간격 확인, 형식 검사·저장, 실패한 부분 재생성, 알림을 차례로 처리합니다.

**반영:** 2026년 11월 1일 실제 월간 리포트를 이 파이프라인으로 만들었습니다.

## 그 밖의 설계

- **수치는 회원 DB에서:** "지난주 벤치 몇 kg 들었지?"에 지어낸 숫자로 답하면 코치로서 신뢰를 잃습니다. 기록을 묻는 말이면 회원 DB를 읽기 전용으로 조회해 그 값을 근거로 답합니다.
- **건강 데이터는 동의 범위 안에서:** 민감 정보 동의를 받은 항목만 대화에 쓰고, 관측 도구에는 가명 처리한 회원 식별자만 남깁니다.
