## 구조 결정

### 1. 일반 대화: 지식 베이스와 여러 호출 경로 대신 모델 하나·경로 하나

**왜:** 일반 대화에는 지식 베이스 검색, 도구 호출 판단, 가벼운 응답용 경로, 상위 모델 승격까지 갈래가 많았습니다. 그중 한 API 경로에서는 프롬프트 캐시가 13번 호출 중 한 번도 적중하지 않았습니다. 매 대답 앞에서 요청을 분류하는 AI 호출(이하 판단기)은 응답 시간 중앙값이 9.5~15.7초였습니다.

**검증:** 지식 베이스를 빼기 전에, 따로 떼어 둔 200문항으로 시험했습니다. 지식 베이스 없이 모델이 혼자 답한 답의 99.0%가 사실 검사를 통과했습니다. 반면 200문항 가운데 지식 베이스로 답할 수 있던 문항은 90.0%에 그쳤습니다.

**바꾼 구조:** 지식 베이스·도구 호출 판단·경로 분기를 걷어내고 모델 하나와 호출 경로 하나로 합쳤습니다. 판단기도 같은 모델로 바꾸고 추론 단계를 껐습니다. 식단·프로필 데이터는 판단기 신호를 보고 코드가 미리 가져옵니다.

**결과와 반영:** 2026년 8월 서버에 배포한 뒤 시험 대화 5턴을 Langfuse로 측정했습니다. 프롬프트 캐시는 판단기가 2턴째, 응답 모델이 3턴째부터 계속 적중했고, 판단기 응답 시간 중앙값은 1.3~1.8초로 줄었습니다. 운영 서버에서도 베타 기간(9.13–9.30) 채팅 대답에 들어간 입력 토큰의 58%를 프롬프트 캐시에서 읽었습니다.

### 2. 기록 변경: 한 번에 다 정하던 AI 호출 대신 단계별 루프

**왜:** 대화로 운동·식단 기록을 바꿀 때, AI 호출 한 번이 무엇을 바꿀지 고르고 값을 채우고 더 할 일이 있는지까지 정했습니다. 그래서 루틴을 추천받고 "넣어줘"라고 하면, 바꿀 내용을 보여 주고 회원 승인을 받는 확인 창에 종목 일부(3~4개)만 담기는 일이 생겼습니다. 같은 사례를 10번 재현하면 9번 그랬습니다.

**바꾼 구조:** 요청마다 분류 → 실행 → 검사 → 응답을 차례로 도는 루프로 바꿨습니다. 회원의 부탁은 하나씩 목록에 올리고, 부탁마다 반영됐는지 거절됐는지를 코드가 끝까지 확인해 말없이 빠지는 부탁이 없게 했습니다.

**검증(개발 환경):** 같은 실패 사례를 10번 재현해 이전 구조와 비교했고, 46개 상황으로 대화 232건을 돌려 다시 시험했습니다.

**결과:** 확인 창에 일부만 담기는 일이 10번 중 9번에서 0번이 됐습니다. 대화 232건 중 228건이 끝까지 반영됐고, 그중 214건은 회원이 처음 한 말 한 번으로 바로 반영됐습니다.

**반영:** 개발 브랜치에서 이 구조로 전면 교체했고(이전 구조로 돌아가는 스위치 없음), 운영 배포 전 시험을 이어 가고 있습니다.

### 3. 대답 앞 판단: 분류용 AI 호출 대신 결정 모델

**왜:** 판단기는 요청 분류와 회원 정보 추출에 더해 8월 말부터 기록 조회 SQL까지 한 호출에서 냈고, 추론도 다시 켜 두었습니다. 이 호출이 끝나야 답을 쓰기 시작할 수 있었고, 분류가 틀려도 어디가 틀렸는지 찾기 어려웠습니다.

**바꾼 구조:** 분류는 결정 모델(OpenAI Decisions API)에 맡겼습니다. 결정 모델은 글을 쓰지 않고, 정해 둔 질문에 예/아니오 확률이나 고른 보기만 돌려줍니다. "기록을 바꿔 달라는 말인가", "지난 대화를 떠올려야 하나" 같은 질문 13개를 한 번에 묻고, 확률이 기준값을 넘는지 보고 코드가 다음 단계를 정합니다. SQL과 답글은 AI 호출이 따로 쓰고, 회원 정보 추출은 답을 보낸 뒤에 합니다.

**검증(개발 환경):** 같은 코칭 대화 12턴 대본을 바꾸기 전 서버와 바꾼 서버에 넣어 호출별 시간과 비용을 비교했습니다. 바꾼 직후에는 같은 뜻의 말에도 확률이 크게 갈려서("지워줄래?" 1.00, "빼주세요" 0.23), 질문마다 정답 세트를 만들어 질문 문장과 기준값을 다시 골랐습니다.

**결과:**
- 대답 앞 판단 시간이 2.65초에서 0.40초로 줄었습니다(12턴 대본 중 기록 조회가 없는 8턴의 중앙값). 대답 전체 시간 중앙값은 10.55초에서 바꾼 직후 8.70초, 문제를 고친 뒤 9.39초가 됐습니다.
- 결정 모델 호출은 캐시가 되지 않아 한 번에 약 0.4원으로, 예상의 5배였습니다. 기록을 묻는 대답은 SQL을 따로 쓰느라 비용이 1.4~1.5배가 됐습니다. 대신 기록 조회가 없는 대답이 약 20% 싸져서, 대답 한 번의 평균 비용은 바꾼 직후 +2.7%, 고친 뒤 −3.4%로 거의 그대로였습니다.
- 바꾼 직후에는 기록 변경 요청을 놓치는 경우가 생겼습니다. 저장해 둔 대화 500턴 중 17턴이었고, 이전 구조는 0턴이었습니다. 질문 문장과 입력을 고쳐 1턴으로 줄였고, 남은 1턴은 확인 창을 거절하는 말이어서 놓쳐도 기록에 영향이 없었습니다.
- AI 코치가 자기에 대해 한 말을 저장하는 추출 호출도, 그런 말이 있었는지 결정 모델에 먼저 묻게 했습니다. 실제 기록으로 다시 돌려 보니 자기 이야기가 없던 코치 글 109건 중 75건(68.8%)에서 추출을 건너뛰었고, 저장해야 했던 28건은 모두 잡았습니다.

**옮기지 않은 것:** 회원이 확인 창에 "응", "아니"로 답한 것을 읽는 승인 판정도 결정 모델로 시험했습니다. 0.3초로 빨랐지만, 코치의 다른 질문에 "좋아요!"라고 답한 것을 승인으로 읽었습니다. 그때도 확률이 0.9가 넘어 기준값으로 걸러낼 수 없었습니다. 판정 문장을 다듬을 때 쓴 정답 세트 222건에서도 정확도가 88.9%로, 지금 방식(93.7%, 11월 5일 측정)보다 낮았습니다. 그래서 승인 판정은 AI 호출에 그대로 두었습니다.

**반영:** 개발 브랜치에서 판단기를 걷어내고 전면 교체했습니다. 운영 배포 전입니다.

### 4. 기록 변경 응답 시간: 기록 조회를 늘 돌리는 대신 변경 요청엔 건너뛰기

**왜:** 2번 구조를 다시 시험할 때, 기록 변경과 기록 조회가 함께 도는 대답이 느렸습니다. 가장 느린 10%는 33.1초 이상 걸렸습니다(p90).

**바꾼 구조:** 요청이 기록 변경으로 분류되면 그 대답에서는 기록 조회 단계를 돌리지 않게 했습니다.

**결과:** 다음 시험에서 같은 대답의 p90 응답 시간이 16.0초로 줄었고(−52%), 156번 중 25초를 넘은 대답은 없었습니다(개발 환경).

### 5. 월간 리포트: 실시간 호출 대신 Batch API

**왜:** 매달 1일 대상 회원 전원의 종합 리포트를 만드는 일은 하루 안에만 끝나면 되는 작업이라, 단가가 절반인 Batch API를 골랐습니다.

**구조:** Batch API는 결과가 최대 24시간 뒤에 오는데 Lambda 하나는 최대 15분까지만 돌아갑니다. 그래서 Step Functions가 Lambda 여섯 개(접수 → 요청 파일 생성 → 제출 → 10분 간격 확인 → 형식 검사·저장·실패 섹션 재생성 → 알림)를 잇고 기다리는 일을 맡습니다.

**결과와 반영:** 리포트 1건당 생성 단가가 약 71원에서 약 35원으로 절반이 됐습니다(테스트 리포트 한 건의 토큰 수로 계산한 추정치). 2026년 11월 1일 실제 월간 리포트를 이 파이프라인으로 만들었습니다.

## 그 밖의 설계

- **기록 변경은 확인 후 실행:** 모델은 바꿀 내용을 제안만 하고, 회원이 확인 창에서 승인해야 코드가 실행합니다.
- **수치는 회원 DB에서:** "지난주 벤치 몇 kg 들었지?"에 지어낸 숫자로 답하면 코치로서 신뢰를 잃습니다. 기록을 묻는 말이면 그 턴에 조회 SQL을 만들어 회원 DB를 읽기 전용으로 읽고, 모델의 기억이나 추측 대신 읽은 값을 근거로 답합니다. 기록을 바꾸는 길은 앱 백엔드 API 하나로만 두었습니다.
- **기억은 둘로 나눔:** 대화 흐름은 롤링 요약으로 이어 가고, 목표·부상·취향 같은 회원 사실은 Qdrant에 따로 쌓아 필요한 턴에만 꺼냅니다.
- **건강 데이터는 동의 범위 안에서:** 민감 정보 동의를 받은 항목만 대화에 쓰고, 관측 도구에는 가명화한 회원 식별자만 남깁니다.
