# content/

사이트에 보이는 글은 모두 이 폴더에 있습니다. 파일을 고치고 `main`에 머지하면 배포됩니다. DB나 관리자 페이지는 쓰지 않습니다.

| 경로 | 내용 |
|---|---|
| `profile.yaml` | 이름, 한 줄 소개, "소개"(`about`, Markdown), 경력(회사만)·학력(`mark`: 동그라미 안 글자, `logo`: 있으면 글자 대신 그 이미지 — `public/images/orgs/`, 정사각형), "걸어온 길" 타임라인(`timeline`: 활동 하나에 한 줄 — 입사·졸업·교육 과정·대회·전시, 그 안의 수상·성적·프로젝트는 `items`, 사진은 `photos`. 최신순. 형식은 파일 안 주석) |
| `projects/<slug>.md` | 프로젝트 하나에 파일 하나. 파일 이름이 주소가 됩니다(`/projects/<slug>`) |
| `blog/<id>.md` | 블로그 글. `/blog/<id>`로 보이고 첫 화면 "글"에 나열됩니다 |
| `skills.yaml` | 첫 화면 "기술" 배지. 대표 기술만 중요한 순서로 적습니다. 라이브러리 단위 세부 항목은 각 프로젝트 `tags`에 둡니다 |
| `_backup/2026-11-10/` | 이전 전 DB 원본(공개 API 응답 그대로). 고치지 않습니다 |

이미지와 영상은 `frontend/public/` 아래에 두고 `/images/...`, `/videos/...` 경로로 씁니다.
프로젝트용은 `public/images/projects/<slug>/`, 대외 활동용은 `public/images/activity/<이름>/`입니다.

## 프로젝트 파일

```markdown
---
title: 요기어때?
summary: 목록에 보이는 한두 문장. 무엇을 만들었고 무엇이 달라졌는지. 합니다체(…입니다/…했습니다.)
org: 소속이나 대회·과정 이름          # 선택
period:
  start: 2025-09
  end: 2025-11                      # 없으면 진행 중
role: 맡은 역할 한 줄
team: AI 4                          # 선택
status: shipped | completed | in-progress | archived
featured: true                      # 첫 화면 "선택한 작업"에 노출
order: 4                            # 작을수록 앞
category: AI
tags: [Python, RAG]
awards: [수상명]                     # 선택
responsibilities:                   # 선택. "내가 맡은 일". ' — ' 앞은 굵게 보입니다
  - 추천 파이프라인 — LLM 대화로 프로필을 받고 벡터 검색으로 후보를 찾는 흐름 설계
metrics:                            # 선택. 숫자에는 범위를 꼭 붙입니다
  - value: −52%
    label: 무엇의 수치인지
    scope: 어디서 어떻게 잰 값인지
    group: 기술 개선                 # 선택. 같은 group끼리 소제목 아래 모입니다
    before: 33.1                    # 선택. before·after를 함께 주면 전후 막대로 그립니다
    after: 16.0
    unit: 초                        # 선택. 숫자 뒤에 붙는 단위
  - value: 98%
    label: 요청 최종 반영률
    scope: 46개 상황 대화 232건
    part: 228                       # 선택. part·whole을 함께 주면 비율 막대로 그립니다
    whole: 232
    unit: 건
links:                              # 있는 것만
  github: ...
  website: ...
  appstore: ...
  playstore: ...
  demo: ...
  video: /videos/projects/<slug>/demo.mp4
  slides: ...
cover: /images/projects/<slug>/thumbnail.png
gallery: [...]
part_of: <slug>                     # 다른 프로젝트의 일부일 때
merged_into: <slug>                 # 합쳐져 더 이상 보이지 않을 때
note: 메모                          # 화면에 안 보임
---

본문(Markdown)
```

- `status: archived`는 목록에 보이지 않습니다. 파일은 기록으로 남깁니다.
- 본문은 "구조 결정"마다 **왜** → **구조**(이전 방식을 바꿨으면 **바꾼 구조**) → **검증** → **결과**(측정 범위) 순서로 씁니다. 검증과 결과는 실제로 확인한 것이 있을 때만 씁니다. 원래 기록에서 이유를 댈 수 없는 결정은 "그 밖의 설계"에 한 줄로 둡니다(결정 블록이 하나도 없으면 "설계"). 제목은 "영역: A 대신 B" 꼴을 권장합니다.
- 장애·기본 구현(배포·권한·인프라) 이야기와 기능 개수는 구조 결정으로 이어진 경우가 아니면 쓰지 않습니다. 원래 기록에 없는 이유·효과는 지어내지 않습니다.
- 수치는 사전 검증·베타·개발 환경처럼 잰 범위를 `scope`와 본문에 함께 적습니다.

## 블로그 글

```markdown
---
title: 글 제목
excerpt: 목록 설명과 검색 설명에 쓰이는 두세 문장
tags: [JEPA, Embedding]
category: insight
read_time: 8                          # 분. 본문 글자 수 ÷ 550 정도
published_at: '2026-11-10T04:00:00Z'  # 목록은 이 값의 최신순
---
```

- AI 엔지니어 일에 관한 인사이트 글입니다. 바깥에서 일어난 일(모델 출시, 연구, 가격·속도 변화)을 소개하고, 그 일이 LLM 앱 구조에서 무엇을 바꾸는지 내 관점에서 따져 봅니다. 회사 프로젝트 이야기는 프로젝트 페이지에 둡니다.
- 본문과 `excerpt`는 사이트의 다른 페이지처럼 합니다체로 씁니다(1인칭은 "저/제가"). 제목과 소제목은 짧은 제목체로 둡니다.
- 흐름: 구체적인 사건이나 숫자로 시작 → 원문이 실제로 말한 것(링크와 정확한 인용) → 원문과 구분한 내 해석 → 기존 구조에 대입한 계산 → 아직 모르는 것.
- `published_at`은 본문이 인용한 자료 가운데 가장 늦게 나온 것보다 뒤여야 합니다. 그 날짜에 알 수 없던 내용(이후 출시, 이후 개정된 지수 등)은 쓰지 않고, 다른 글로 거는 링크는 그보다 먼저 나온 글만 가리킵니다.
- 수치에는 출처 링크와 조건(표본 크기, 벤치마크 하나, 회사 발표 숫자, 프리프린트)을 함께 적습니다. 계산은 독자가 다시 해 볼 수 있게 식을 보여 주고, 설명용으로 정한 숫자는 가정이라고 밝힙니다.
- 한눈에 들어오게 씁니다.
  - 맨 위에 `> **한눈에 보기**` 상자를 두고, 숫자가 들어간 핵심 주장 3~4줄을 목록으로 적습니다.
  - 원문 소개와 내 재해석이 섞이지 않게, 재해석은 `> **제 해석**` 상자에 둡니다(글마다 1~3개).
  - 비교하는 숫자(가격, 구조 A/B, 설정별 결과)는 표로, 나열은 목록으로 씁니다. 계산 과정은 코드 블록으로 남겨 다시 해 볼 수 있게 합니다.
  - 굵은 글씨는 핵심 어구에만 짧게 쓰고, 문단은 두세 문장 단위로 끊습니다.
- 쓰지 않는 것: TL;DR·Key Takeaways·Further Reading 같은 정형 틀, 숫자 없는 구호, 표와 목록이 문단의 논리를 대신하는 글, "A가 아니라 B" 대구의 반복, 긴 줄표(—), 겪지 않은 경험.
