> **한눈에 보기**
> - AWS는 11월 11일 공개한 AWS Emulator의 코드를 **에이전트가 전부 썼고 팀은 쓰지도 리뷰하지도 않았다**고 밝혔습니다. 공개 저장소 기준으로 출시까지 약 20일 동안 코드 변경 기록(커밋)이 29,684개, 하루 약 1,480개입니다.
> - 사람의 리뷰가 있던 자리에는 **실제 AWS에서 먼저 통과시킨 테스트 약 4만 3천 개**와, 모든 변경이 거쳐야 하는 자동 관문이 들어갔습니다.
> - 릴리스(새 버전을 묶어 내놓는 것)마다 공개되는 점수 파일을 세어 보면, **실제 AWS와 똑같이 동작한 테스트**는 출시 시점에 56.5%, 11월 14일 릴리스에서 65.5%입니다. 서비스별로는 SQS 77.5%부터 CloudFormation 22.7%까지 벌어집니다.
> - 권한 검사는 실제 AWS와 다르게 동작한다고 AWS가 직접 적었습니다. 리뷰를 빼려면 **스펙, 기계로 대조할 정답지, 공개된 점수**가 필요한데, LLM(ChatGPT 같은 서비스의 바탕이 되는 언어 모델)으로 만드는 앱에는 정답지가 일부 기능에만 있습니다.

11월 11일 AWS가 낸 [글](https://www.aboutamazon.com/news/aws/how-autonomous-ai-agents-built-aws-emulator)에 이런 문장이 있습니다. "The emulator was written entirely by autonomous agents. Our team hasn't written or reviewed any of the code." 에뮬레이터는 전부 자율 에이전트(스스로 코드를 읽고 고치며 일하는 AI)가 썼고, 팀은 코드를 한 줄도 쓰거나 리뷰하지 않았다는 말입니다. 리뷰는 다른 사람이 쓴 코드를 합치기 전에 읽고 확인하는 일입니다.

개발자 커뮤니티 Hacker News의 [스레드](https://news.ycombinator.com/item?id=50456631)는 제가 읽은 11월 16일 기준 991점, 댓글 266개였습니다. AI가 쏟아 낸 결과물로 보이는데 정확도를 어떻게 믿느냐는 댓글과, 이렇게 테스트로 바로 확인되는 일이야말로 AI에게 맡기기 가장 좋은 종류라는 댓글이 같이 달렸습니다. 독일 IT 매체 heise는 AWS가 자랑한 대목이 오히려 [역풍을 맞았다](https://www.heise.de/en/news/AWS-Emulator-in-detail-The-whole-cloud-on-your-own-computer-11524820.html)고 썼습니다.

저는 "리뷰를 안 했다"는 문장보다 그 자리에 무엇을 넣었는지가 궁금했습니다. AWS가 숫자를 공개해 뒀기 때문에 직접 세어 볼 수 있습니다.

## 무엇이 나왔나

AWS는 아마존이 서버와 저장 공간을 인터넷으로 빌려주는 클라우드 서비스입니다. 에뮬레이터는 진짜를 흉내 내는 프로그램입니다. AWS Emulator는 AWS에 접속하지 않고도 내 컴퓨터에서 AWS에 요청을 보낸 것처럼 응답을 돌려줍니다. 파일을 저장하는 S3, 메시지를 줄 세워 전달하는 SQS 같은 서비스를 요금 없이, 인터넷 없이 시험해 볼 수 있습니다.

| 항목 | 내용 |
|---|---|
| 공개 | 2026년 11월 11일, [정식 출시](https://aws.amazon.com/blogs/aws/test-your-applications-against-aws-locally-with-aws-emulator/) |
| 범위 | API 모델 400개 이상, 서비스 200개 이상 |
| 요금과 라이선스 | 무료. 코드는 저작권을 포기하는 CC0로 [GitHub](https://github.com/aws/aws-emulator)에 공개 |
| 바깥 기여 | 버그 신고는 받지만 코드 변경 제안(PR)은 받지 않음 (저장소 안내문) |
| 한계 | 상태를 메모리에만 두어서 끄면 사라짐 ([출시 공지](https://aws.amazon.com/about-aws/whats-new/2026/11/aws-emulator-now-available/)). 계정은 하나로 고정 (출시 글) |

API 모델은 서비스마다 어떤 요청을 받고 무엇을 돌려주며 어떤 오류를 내는지 적어 둔 명세 파일입니다. AWS는 이 파일을 공개해 두고 있습니다.

시작은 주말 실험이었습니다. 글을 쓴 AWS의 수석 엔지니어 Matthew Goldberg는 올해 2월 Anthropic이 공개한 [C 컴파일러 실험](https://www.anthropic.com/research/building-c-compiler)에서 생각을 얻었다고 적었습니다. 컴파일러는 사람이 쓴 코드를 실행 파일로 바꾸는 프로그램이고, 이 실험에서는 에이전트 16개가 2,000번 가까운 작업 세션으로 10만 줄짜리 컴파일러를 만들었습니다.

Goldberg의 가설은 이랬습니다. 잘 정의된 **스펙**(무엇이 맞는 동작인지 적은 문서)과 대조해 볼 **기준 구현**(실제로 돌아가는 진짜)이 있으면, 에이전트가 그 스펙을 충실히 따르는 결과물을 혼자 만들 수 있다는 것입니다.

AWS에는 둘 다 있습니다. 스펙은 공개된 API 모델이고 기준 구현은 실제 AWS입니다. 이 글에서는 기준 구현을 **정답지**라고 부르겠습니다.

그가 AWS의 코딩 에이전트 Kiro에게 준 지시는 세 줄이었습니다. 테스트(코드가 기대대로 동작하는지 자동으로 확인하는 작은 프로그램)를 쓰고, 그 테스트가 실제 AWS에서 통과할 때까지 고치고, 같은 테스트를 통과하면서 내 컴퓨터 메모리에서만 도는 프로그램을 만들라는 것입니다. 15분 뒤 쓸 만한 SQS 첫 버전이 나왔고, 주말 동안 나머지 서비스를 만들게 했다고 합니다.

그는 바로 뒤에 이렇게 덧붙입니다. "Turning that into a robust product took more than a weekend." 튼튼한 제품으로 만드는 일은 주말 한 번으로는 되지 않았다는 말입니다.

## 리뷰가 있던 자리에 놓인 것

AWS Emulator는 세 팀의 에이전트가 만듭니다.

1. **테스트를 쓰는 팀.** API 모델을 보고 "큐를 만들고, 메시지를 보내고, 받고, 지운다" 같은 실제 사용 흐름을 테스트로 씁니다. 테스트는 제출 전에 실제 AWS에서 먼저 통과해야 합니다. AWS는 이것을 충실도 테스트(fidelity test)라고 부릅니다.
2. **차이를 찾는 팀.** 그 테스트를 에뮬레이터에 돌려서 실패한 것을 이슈(고쳐야 할 일 한 건)로 올립니다.
3. **고치는 팀.** 에이전트 하나가 이슈 하나를 맡아 원인을 찾고 코드를 고칩니다.

고친 코드는 **머지 게이트**를 지나야 본 코드에 합쳐집니다. 머지 게이트는 변경이 합쳐지기 전에 통과해야 하는 자동 검사 관문입니다. Goldberg의 글과, 같은 날 나온 AWS 임원 Swami Sivasubramanian의 [글](https://www.allthingsdistributed.com/2026/11/aws-emulator-and-the-engineers-job-when-agents-write-the-code.html)을 합치면 변경을 걸러 내는 검사는 이렇습니다. 오른쪽 열의 구분은 두 글을 읽고 제가 나눈 것입니다.

| 변경을 걸러 내는 검사 | 판정하는 근거 (제 구분) |
|---|---|
| 컴파일(코드를 실행 파일로 바꾸는 일)이 되는가 | 기계적 판정 |
| 이미 맞던 동작이 틀리게 되지 않았는가 | 실제 AWS에서 검증해 둔 충실도 테스트의 결과로 판정하는 것으로 보임 |
| 건드리면 안 되는 코드를 건드리지 않았는가 | 결정론적 검사 (같은 입력이면 언제나 같은 판정). 게이트 안에 있는지는 글에 분명히 나오지 않음 |
| 코딩 표준을 지켰는가 | 리뷰하는 에이전트의 판단 |
| 코드가 안전한가 | 서로 다른 공격 방식을 보는 보안 에이전트 여러 개의 판단 |

Goldberg는 이 게이트를 두고 "Without this merge gate, we wouldn't trust what our agents are building"이라고 썼습니다. 게이트가 없었다면 에이전트가 만든 것을 믿지 않았을 거라는 말입니다.

글에는 테스트만으로는 방향을 잡지 못한 일화도 나옵니다. 이전 버전에서 에이전트들은 Lambda(서버 없이 코드를 실행해 주는 서비스)를 흉내 내려고 Python 실행기를 처음부터 직접 만들기로 했습니다. 팀은 그 뒤 이미 있는 라이브러리를 쓰라는 지침을 줬다고 합니다.

Goldberg는 이 구조를 색칠 공부 책에 빗댑니다. 에이전트는 말을 안 듣는 게 아니라 아직 솜씨가 모자란 것이고, 그래서 칠할 칸이 그려진 책이 필요하다는 것입니다.

> **제 해석**
>
> 사람이 하던 리뷰는 자동 검사 쪽으로 **자리를 옮겼습니다.** 3월에 쓴 [하네스 엔지니어링 글](/blog/harness-engineering)에서 하네스(모델 바깥에서 에이전트의 일을 잡아 주는 장치 전체)를 알려 주는 장치와 확인하는 장치로 나눴는데, 이 팀이 사람 손으로 만든 것은 거의 다 확인하는 장치입니다. 세 팀이 일하는 흐름, 머지 게이트, 릴리스 과정이 그렇습니다. Python 실행기 일화는 반대쪽을 보여 줍니다. 제가 보기에 그건 테스트는 통과할 수 있어도 방향이 이상한 결정이고, 그런 판단은 결국 "있는 라이브러리를 쓰라"는 알려 주는 장치로 메웠습니다.

## 사람이 리뷰했다면

공개 저장소의 첫 커밋은 10월 21일이고, 출시 릴리스에 묶인 마지막 커밋은 11월 10일입니다. 커밋은 코드 변경을 저장소에 기록한 한 단위입니다. 사람이 리뷰를 했다면 얼마나 들었을지 가정을 하나 두고 계산해 봤습니다.

```
기간        2026-10-21 → 2026-11-10, 약 20일
커밋        29,684개 ÷ 20일 ≈ 하루 1,484개

가정: 커밋 하나를 읽는 데 10분
리뷰 시간   29,684 × 10분 ≈ 4,947시간
필요한 사람  4,947시간 ÷ (20일 × 하루 8시간) ≈ 31명

가정을 5분으로 줄이면
필요한 사람  2,474시간 ÷ 160시간 ≈ 15명
```

리뷰만 하는 사람이 쉬는 날 없이 31명, 시간을 절반으로 잡아도 15명 필요합니다. 10분과 5분은 제가 정한 숫자입니다.

두 가지를 감안해야 합니다. 이 20일은 지금 버전의 공개 저장소 기록이고, Goldberg는 그 전에도 에이전트가 여러 버전을 다시 만들었다고 적었습니다. 그리고 AWS는 내부 저장소에서 작업한 뒤 묶어서 공개한다고 했으니, 내부의 실제 변경 횟수는 다를 수 있습니다.

하루 약 1,480개를 사람이 다 읽기는 어렵습니다. 그래서 저는 리뷰를 대신한 장치가 얼마나 일했는지를 봤습니다.

## 점수표를 세어 보면

AWS는 릴리스마다 `scores.json.gz`라는 점수 파일을 붙입니다. 테스트 하나하나가 통과했는지 실패했는지, 실패했다면 몇 번째 단계에서 무엇이 달랐는지 적힌 파일입니다. 이 글에서는 점수표라고 부르겠습니다.

통과 기준은 까다롭습니다. 호출마다 상태 코드, 응답 내용, 오류 코드와 오류 문구까지 실제 AWS와 같아야 하고, 그 결과 만들어진 자원과 데이터도 같아야 합니다.

출시 릴리스([v1.0.322](https://github.com/aws/aws-emulator/releases/tag/v1.0.322))와 11월 14일 릴리스([v1.0.385](https://github.com/aws/aws-emulator/releases/tag/v1.0.385))의 점수표를 내려받아 세어 봤습니다.

| | 출시 릴리스 | 11월 14일 릴리스 |
|---|---|---|
| 전체 테스트 | 42,937개 | 43,548개 |
| 통과 | 24,243개 | 28,505개 |
| 통과율 | **56.5%** | **65.5%** |

많이 쓰는 서비스 일곱 개를 골라 보면 이렇습니다. 여러 서비스를 함께 쓰는 테스트는 관련된 서비스마다 한 번씩 셌습니다.

| 서비스 | 하는 일 | 출시 릴리스 | 11월 14일 릴리스 |
|---|---|---|---|
| SQS | 메시지를 줄 세워 전달 | 67.8% | 77.5% |
| S3 | 파일 저장 | 62.7% | 72.4% |
| DynamoDB | 데이터베이스 | 68.1% | 72.0% |
| IAM | 권한 관리 | 58.0% | 67.0% |
| Lambda | 서버 없이 코드 실행 | 51.9% | 63.3% |
| EC2 | 가상 서버 | 38.8% | 49.9% |
| CloudFormation | 인프라를 설정 파일로 한꺼번에 생성 | 18.9% | 22.7% |

점수표는 API 모델마다 서비스를 따로 세기 때문에 AWS가 말한 서비스 수보다 항목이 많습니다. 그중 테스트가 20개 이상인 303개를 보면, 통과율 90% 이상인 서비스가 38개에서 62개로 늘었고 50% 미만인 서비스는 95개에서 52개로 줄었습니다.

저장소에는 점수 말고 목록도 있습니다. 아직 실제 AWS와 다른 동작은 `issues/things-that-do-not-work` 폴더에, 고친 것은 `issues/things-that-now-work` 폴더에 항목 하나당 파일 하나로 쌓입니다. 두 릴리스 사이에 파일 수가 이렇게 바뀌었습니다.

```
고친 항목     12,709 → 14,500   (+1,791)
남은 항목      6,545 →  6,419   (−126)
새로 찾은 항목  1,791 − 126 = 1,665

두 릴리스의 마지막 커밋 사이 약 3.9일
(11월 10일 저녁 → 11월 14일 저녁, 협정 세계시)
하루에 약 460개를 고치고, 약 430개를 새로 찾음
```

고치는 속도와 새로 찾는 속도가 거의 같습니다. 통과율은 9%p(퍼센트포인트) 올랐는데 남은 목록은 2%도 줄지 않았습니다. 차이를 찾는 팀이 새 항목을 계속 올리기 때문으로 보입니다. 같은 기간 테스트는 611개 늘었습니다. AWS도 테스트가 늘면 에뮬레이터가 좋아지는 동안에도 점수가 내려갈 수 있다고 적어 뒀습니다.

Goldberg의 글에는 하루에 이슈 수천 개가 고쳐진다는 문장이 있습니다. 공개 저장소의 이 기간은 하루 약 460개인데, 내부에서 세는 이슈와 공개 폴더의 파일이 같은 단위인지는 알 수 없어서 그대로 견주기는 어렵습니다.

> **제 해석**
>
> 논란은 "리뷰하지 않았다"에 몰렸지만, 저는 이 점수표가 더 큰 소식이라고 봅니다. 사람이 꼼꼼히 리뷰한 코드에도 보통 "어느 기능이 몇 % 맞다"는 표는 붙어 있지 않습니다. 56.5%는 낮은 숫자입니다. 대신 SQS는 써 볼 만하고 CloudFormation은 아직 멀었다는 것을 쓰기 전에 알 수 있습니다.

## 점수표가 보장하지 않는 곳

AWS는 쓰지 말아야 할 곳도 적어 뒀습니다. 출시 글에 에뮬레이터로 앱이 안전한지 시험하지 말라는 문장이 있고, [보안 문서](https://docs.aws.amazon.com/emulator/latest/userguide/security.html)의 첫 항목도 같은 내용입니다. 목록에는 IAM(누가 무엇을 할 수 있는지 정하는 AWS의 권한 체계) 정책, 버킷(S3에서 파일을 담는 통) 정책, 암호화 키 정책, 계정이나 지역을 넘나드는 접근이 있습니다.

문서의 설명은 이렇습니다.

- 일부 서비스는 IAM 정책을 평가하지만 AWS와 같은 방식은 아닙니다.
- 에뮬레이터는 자기가 발급한 키(요청을 보낸 쪽을 확인하는 비밀 값)로 서명한 요청을 거절하지 않습니다.
- 암호화 키 정책과 버킷 정책은 확인하지 않습니다.

그래서 실제 AWS라면 거절할 요청이 에뮬레이터에서는 성공할 수 있고, 반대로 AWS가 허용할 요청이 실패할 수도 있습니다.

운전면허 기능시험장에 빗대면 이렇습니다. 시험장은 차선과 주차 칸을 실제 도로와 똑같이 그려 놨지만 단속 카메라는 없습니다. 시험장에서 과속하고도 아무 일이 없었다고 해서 도로에서도 안 걸린다는 뜻은 아닙니다.

이 대목은 두 가지를 섞어 읽기 쉽습니다.

- **게이트의 보안 에이전트**는 에뮬레이터 코드 자체에 취약점이 없는지 봅니다.
- **문서의 경고**는 사용자가 자기 앱의 권한 설정이 맞는지를 에뮬레이터로 확인하지 말라는 것입니다.

권한 문제는 AWS가 출시 당일 글에 직접 적어 둔 한계입니다. 왜 권한 평가를 맞추지 못했는지는 밝히지 않았습니다. Hacker News의 한 댓글은 에이전트가 공개된 API 모델만 보고 만들었기 때문일 거라고 추측했는데, 확인된 이야기는 아닙니다.

같은 날 나온 AWS의 Matt Wood [글](https://aws.amazon.com/blogs/aws-insights/better-feedback-for-building-with-agents/)에는 에이전트를 평가하고 학습시키는 팀을 다룬 대목에 비슷한 위험이 나옵니다. 에뮬레이터가 AWS라면 거절할 동작을 받아 주면 학습이 그 실수를 굳힐 수 있고, 에이전트가 에뮬레이터의 결함 덕분에만 통하는 지름길을 찾아낼 수도 있다는 것입니다. 권한을 따로 짚은 문장은 아닙니다.

저라면 코딩 에이전트에게 에뮬레이터를 쥐여 주고 "테스트가 통과할 때까지 고쳐라"라고 시킬 때, 권한에 관한 부분은 실제 AWS에서 한 번 더 확인하는 단계를 따로 두겠습니다. AWS 문서도 운영에 올리기 전에 보안 설정을 실제 AWS에서 시험하라고 적었습니다.

## LLM 앱에 대입하면

저는 다른 회사가 제공하는 LLM을 불러 써서 에이전트를 만드는 쪽입니다. 이 사례에서 가져올 것을 조건 세 가지로 정리해 봤습니다.

| 조건 | AWS Emulator | LLM 앱 |
|---|---|---|
| 무엇이 맞는지 적은 스펙 | 기계가 읽는 API 모델 | 대개 요구 사항 문서와 프롬프트(모델에게 주는 지시문). 기계가 바로 대조할 형식은 아님 |
| 기계로 대조할 정답지 | 실제 AWS | 일부 기능에만 있음 |
| 공개된 점수 | 릴리스마다 테스트별 결과 | 평가 세트(미리 모아 둔 시험 문제 묶음)를 만들어 둔 팀만 가짐 |

차이는 둘째 줄에서 납니다. 고객 상담 에이전트를 가상의 예로 들면 이렇게 나뉩니다.

- **정답지를 만들 수 있는 것:** 환불 요청을 환불 도구로 보냈는가, 주문 번호를 형식에 맞게 넘겼는가, 금액 계산이 맞는가
- **정답지가 없는 것:** 설명이 이해하기 쉬웠는가, 말투가 상황에 맞았는가

학교 시험으로 치면 앞쪽은 객관식이라 채점 기계에 맡길 수 있고, 뒤쪽은 논술이라 누군가 읽어야 합니다. 논술 채점을 LLM에게 맡길 수는 있습니다. 다만 그 채점도 또 하나의 판단입니다.

> **제 해석**
>
> 사람의 리뷰를 뺄 수 있는 범위는 **정답지로 채점할 수 있는 범위까지**라고 봅니다. AWS Emulator에서도 점수표가 보장하지 못하는 권한 평가는 쓰지 말라고 문서에 적혔습니다. LLM 앱이라면 도구 선택, 출력 형식, 분류처럼 정답지를 만들 수 있는 부분부터 게이트로 옮기고, 답변 품질처럼 판단이 필요한 부분은 사람이 표본을 읽는 단계를 남기는 게 맞다고 봅니다. 하네스 글 끝에 "LLM이 판정하는 검사도 남는가"를 모르는 것으로 적어 뒀는데, AWS의 게이트에도 코딩 표준과 보안처럼 에이전트가 판정하는 검사가 섞여 있습니다. 그 검사가 얼마나 놓치는지는 이번 글들에 숫자가 없습니다.

## 아직 모르는 것

- **점수가 어디까지 오를지.** 두 릴리스 사이에 9%p 올랐지만 새로 찾는 속도가 고치는 속도와 비슷합니다. CloudFormation처럼 여러 서비스가 얽힌 쪽은 아직 20%대입니다.
- **테스트가 보지 않는 동작.** 테스트도 에이전트가 API 모델을 보고 만듭니다. 아무도 테스트로 쓰지 않은 동작은 틀려도 통과합니다. 65.5%는 테스트한 것 중에서 센 숫자입니다.
- **에이전트가 판정하는 검사의 정확도.** 보안 에이전트가 문제를 얼마나 잡고 얼마나 놓치는지는 공개되지 않았습니다. Goldberg는 품질과 보안 기준을 어떻게 지키는지 후속 글에서 다루겠다고 예고했습니다.
- **드는 비용.** 에이전트 수천 개를 돌리는 데 든 토큰(모델이 글을 쪼개 세는 단위이자 요금 단위) 비용은 어디에도 없습니다. Anthropic의 컴파일러 실험에는 2만 달러 가까이 들었습니다. 위에서 계산한 31명과 견주려면 AWS 쪽의 이 숫자가 필요합니다.
