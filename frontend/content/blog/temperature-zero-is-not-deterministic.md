> **한눈에 보기**
> - Thinking Machines Lab이 Qwen3-235B에 같은 프롬프트를 temperature 0으로 **1,000번** 보냈더니 서로 다른 답이 **80가지** 나왔습니다. 계산 방식을 바꾼 뒤에는 1,000개가 모두 같았습니다.
> - 원인으로 지목된 것은 **배치 크기**입니다. 내 요청과 함께 계산되는 다른 요청의 수가 서버 부하에 따라 바뀌고, 그에 따라 덧셈 순서가 바뀝니다.
> - 고치는 데는 속도가 듭니다. 원문 측정에서 같은 작업이 **26초에서 42초**로 늘었고, SGLang은 평균 34% 느려졌다고 보고했습니다.
> - API 사용자는 이 계산을 고칠 수 없으니 테스트를 **통과율**로 봐야 합니다. 90% 통과하던 테스트가 80%로 떨어진 것을 가려내려면 계산상 **약 70번**을 돌려야 합니다.

## 같은 질문, 80가지 답

2025년 9월 10일, Thinking Machines Lab의 Horace He와 동료들이 [Defeating Nondeterminism in LLM Inference](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/)를 냈습니다. Qwen3-235B-A22B-Instruct-2507에 리처드 파인만에 대해 알려 달라는 같은 프롬프트("Tell me about Richard Feynman")를 1,000번 보내고, 매번 1,000토큰씩 답을 받은 실험입니다.

temperature(온도)는 모델이 다음 토큰을 얼마나 무작위로 고를지 정하는 값입니다. 토큰은 모델이 글을 읽고 쓰는 단위로, 대략 단어 조각입니다. 이 실험처럼 온도를 0으로 두면 늘 가장 확률이 높은 토큰만 고르므로, 같은 질문에는 같은 답이 나와야 합니다.

- 서로 다른 답이 80가지 나왔고, 가장 많이 나온 답도 1,000번 중 78번이었습니다.
- 처음 102토큰은 모두 같았습니다. "Feynman was born on May 11, 1918, in"(파인만은 1918년 5월 11일 ...에서 태어났다) 다음 자리에 992번은 "Queens, New York"을, 8번은 "New York City"를 썼습니다.
- 한 번 갈라지면 뒤 토큰은 서로 다른 앞 문장을 보고 만들어지므로 차이가 끝까지 이어집니다.

## 덧셈 순서만 바꿔도 값이 달라진다

컴퓨터는 소수점이 있는 수(실수)를 "유효숫자 몇 자리 × 2의 몇 제곱" 꼴로 저장합니다. 이 방식을 부동소수점(floating point)이라고 합니다. 자릿수가 정해져 있어서 더할 때마다 끝자리를 반올림합니다.

원문의 예는 브라우저 개발자 도구(F12) 콘솔에 붙여 넣어 확인할 수 있습니다.

```
(0.1 + 1e20) - 1e20    // 0
0.1 + (1e20 - 1e20)    // 0.1
```

1e20은 1 뒤에 0이 20개 붙은 아주 큰 수입니다. 큰 수에 0.1을 먼저 더하면 0.1이 반올림에 묻혀 사라지고, 큰 수끼리 먼저 빼면 0.1이 남습니다.

원문처럼 유효숫자를 세 자리만 남기는 장부로 옮겨 보면 이렇습니다.

| 더하는 순서 | 계산 | 남는 값 |
|---|---|---|
| 1,000원에 4원을 하나씩 세 번 | 1,004를 세 자리로 줄이면 1,000. 세 번 반복 | 1,000원 |
| 4원 세 개를 먼저 합친 뒤 | 1,000 + 12 = 1,012를 세 자리로 줄이면 1,010 | 1,010원 |

같은 돈을 더했는데 순서에 따라 10원이 차이 납니다. LLM은 토큰 하나를 만들 때마다 이런 덧셈을 수없이 하고, 어느 한 곳의 끝자리 차이가 1등과 2등 후보 토큰의 순위를 뒤집으면 답이 갈라집니다.

## 같은 배치에 탄 다른 요청들

흔한 설명은 GPU 코어가 끝나는 순서에 따라 더하는 순서가 달라진다는 것입니다. 원문은 이 설명이 전부는 아니라고 봤습니다. 같은 행렬 곱셈을 1,000번 반복해도 결과는 비트 하나까지 같았습니다.

같은 요청 묶음을 넣으면 서버는 늘 같은 결과를 냅니다. 문제는 그 **묶음**이 매번 다르다는 데 있습니다.

추론 서버(모델을 돌려 답을 만들어 주는 서버)는 GPU를 놀리지 않으려고 여러 사용자의 요청을 묶어 한꺼번에 계산합니다. 이 묶음이 배치(batch)입니다. GPU에서 행렬 곱셈 같은 계산 하나를 수행하는 작은 프로그램은 커널(kernel)이라고 부릅니다.

원문이 찾은 원인은 대부분의 커널이 **배치 불변**(batch-invariant)하지 않다는 점입니다. 배치에 요청이 몇 개냐에 따라 커널이 일을 나누는 방식이 바뀌고, 그러면 내 요청 안의 덧셈 순서도 바뀝니다. 주방에 빗대 보겠습니다.

- 주문이 밀려 있으면 요리사마다 한 접시씩 맡아 처음부터 끝까지 만듭니다.
- 주문이 한두 건뿐이면 손이 노는 요리사들이 한 접시를 나눠 맡고 마지막에 합칩니다.
- 같은 요리가 나오지만 재료가 합쳐지는 순서는 다릅니다. 어느 방식이 될지는 그 순간 들어와 있는 **다른 손님의 주문 수**가 정합니다.

요리사는 GPU 코어, 접시는 요청, 재료가 합쳐지는 순서는 덧셈 순서입니다. 손님인 나는 주문이 몇 건 들어와 있는지 알 수도 정할 수도 없습니다. 원문은 이렇게 정리했습니다. "the primary reason nearly all LLM inference endpoints are nondeterministic is that the load (and thus batch-size) nondeterministically varies!" 거의 모든 LLM 추론 서비스에서 같은 입력에 답이 달라지는 주된 이유는 부하, 그리고 그에 따른 배치 크기가 예측할 수 없게 바뀌기 때문이라는 말입니다.

## 배치 불변 커널과 그 비용

고치는 방법은 주문이 몇 건이든 **한 접시는 늘 같은 방식으로** 만드는 것입니다. 손이 노는 요리사가 생겨도 감수합니다. 원문은 많은 수를 더해 하나로 모으는 연산 세 가지(RMSNorm 정규화, 행렬 곱셈, 어텐션)를 이렇게 바꿨고, 오픈소스 추론 엔진 vLLM에서 돌려 볼 수 있는 예제와 함께 공개했습니다.

결정적 모드(같은 입력에 늘 같은 답을 내도록 바꾼 설정)의 속도는 Qwen3-8B를 GPU 한 장에 올려 출력 90–110토큰짜리 요청 1,000개로 쟀습니다. 원문은 최적화에 크게 힘쓰지 않았다고 밝혔습니다.

| 설정 | 걸린 시간 | 기본 대비 |
|---|---|---|
| vLLM 기본 | 26초 | |
| 결정적 모드, 최적화 전 | 55초 | 약 2.1배 |
| 결정적 모드, 어텐션 커널 개선 | 42초 | 약 1.6배 |

그 뒤 오픈소스 추론 엔진들이 같은 방식을 받아들였습니다.

| 구현 | 켜는 방법 | 보고된 비용 | 조건 |
|---|---|---|---|
| [SGLang](https://lmsys.org/blog/2025-09-22-sglang-deterministic/) (2025년 9월 22일) | `--enable-deterministic-inference` | 평균 34.35% 느려짐 | Qwen3-8B, 작업 3종. 발표 당시 dense 모델(토큰마다 모델 전체를 계산하는 구조)만 |
| [vLLM](https://docs.vllm.ai/en/v0.24.0/features/batch_invariance/) (v0.24.0 문서) | `VLLM_BATCH_INVARIANT=1` | 성능이 떨어질 수 있다고만 적음 | 베타. NVIDIA Ampere 세대 이후 GPU |

SGLang 시험(조건마다 답을 50번씩 받음)에서 서로 다른 출력은 일반 모드가 최대 18가지, 결정적 모드가 늘 1가지였습니다. 그래도 SGLang은 이 모드를 주로 디버깅과 재현에 쓰라고("primarily for debugging and reproducibility") 권했습니다.

## 학습하는 쪽에는 더 큰 문제

강화학습(RL)은 모델이 직접 만든 답에 점수(보상)를 매겨 다시 학습하는 방식이고, **on-policy**는 지금 학습하는 바로 그 모델이 만든 답으로 학습한다는 뜻입니다. 답을 만드는 엔진과 학습 엔진의 수치가 조금씩 다르면 사실상 남의 답으로 학습하는 셈입니다.

원문의 실험(8B 모델, 수학 문제)에서 두 엔진의 차이를 보정하지 않고 학습하면 318번째 단계 근처에서 보상이 무너졌고, 두 엔진의 계산을 비트 단위로 맞추자 안정적으로 학습됐습니다. 2025년 11월 vLLM과 TorchTitan 팀의 [실험](https://blog.vllm.ai/2025/11/10/bitwise-consistent-train-inference.html)에서는 같은 방식이 보상을 높였지만 실행이 2.4배 느렸습니다.

## API 위에서 만드는 사람에게

호스팅된 API를 쓰는 쪽은 커널을 고를 수 없습니다. OpenAI는 2023년 `seed` 파라미터(무작위 선택을 고정하는 값)를 [소개하면서](https://cookbook.openai.com/examples/reproducible_outputs_with_the_seed_parameter) "Determinism is not guaranteed", 곧 늘 같은 출력이 나온다고 보장하지는 않는다고 적었습니다. 서버 구성을 알려 주는 `system_fingerprint` 값도 인프라 설정이 바뀌면 달라지고, 그런 변경이 1년에 몇 번 있을 수 있다고 밝혔습니다.

> **제 해석**
>
> 원인이 같은 시간에 들어온 남의 요청이라면, API 사용자에게 비결정성은 버그 리포트로 없앨 문제가 못 됩니다. 결정적 모드는 공개된 측정에서 34–62% 느렸고(62%는 26초가 42초가 된 원문 수치), 처리량(같은 GPU로 처리하는 요청 수)이 곧 원가인 API 회사가 이를 기본값으로 켤 이유는 약하다고 봅니다. 그래서 저는 **같은 입력에 출력이 바뀐다는 전제로** 테스트와 평가를 설계해야 한다고 생각합니다.

평가 점수가 실제로 흔들린 기록도 있습니다.

- 2024년 [한 연구](https://arxiv.org/abs/2408.04667)는 GPT-4o 등 5개 모델을 temperature 0, seed 고정으로 8개 과제에 10번씩 돌렸습니다. 일부 과제에서 정확도의 최고와 최저가 5–15% 벌어졌고, 출력 문장 전체가 같은 경우보다 출력에서 뽑아낸 답이 같은 경우가 훨씬 많았습니다.
- 2025년 6월 [다른 연구](https://arxiv.org/abs/2506.09501)에서는 DeepSeek-R1-Distill-Qwen-7B를 16비트 정밀도(bfloat16)와 온도 0에 해당하는 방식으로 돌렸을 때, GPU 수와 종류, 배치 크기에 따라 정확도가 최대 9% 달라졌습니다.

## 테스트를 통과율로 설계하기

LLM 출력을 검사하는 테스트는 같은 코드로 돌려도 통과했다 실패했다 합니다. 그래서 테스트마다 통과율이 있습니다. 통과율이 높은 테스트도 여러 번, 여러 개 돌리면 실패가 꽤 자주 보입니다.

```
테스트 하나의 실제 통과율이 90%일 때
  5번 돌려 한 번이라도 실패할 확률   1 − 0.9^5  ≈ 41%

테스트 20개의 통과율이 각각 99%일 때
  CI 한 번에 모두 통과할 확률        0.99^20    ≈ 82%
```

코드를 그대로 둬도 CI(코드를 올릴 때마다 테스트를 자동으로 돌리는 장치) 실행의 약 18%가 빨간불입니다. 그럼 진짜 회귀(전에는 되던 것이 안 되게 된 것)는 어떻게 가려낼까요. 90% 통과하던 테스트가 80%로 떨어진 경우를 잡고 싶다고 하겠습니다.

```
p0 = 0.90   지금까지 기록으로 아는 통과율 (가정)
p1 = 0.80   잡아내고 싶은 나빠진 통과율 (가정)
z_a = 1.645 정상인데 회귀로 잘못 볼 확률 5% (한쪽 검정)
z_b = 0.842 실제로 나빠졌는데 놓칠 확률 20%

n = ((z_a × √(p0 × (1 − p0)) + z_b × √(p1 × (1 − p1))) ÷ (p0 − p1))²
  = ((1.645 × 0.3 + 0.842 × 0.4) ÷ 0.1)²
  ≈ 69번
```

90%짜리 테스트가 80%로 나빠진 것을 잡으려면 약 70번은 돌려야 한다는 뜻입니다. z 값은 오탐(정상인데 회귀로 보는 것)과 놓침을 얼마나 허용할지로 정해지는 표준 상수입니다. 식은 근사라서 정확한 확률 분포(이항분포)로도 직접 계산해 봤습니다. 회귀로 볼 통과 횟수 기준은 오탐이 5%를 넘지 않는 범위에서 가장 높게 잡았습니다.

| 돌린 횟수 | 회귀로 볼 기준 | 정상인데 회귀로 볼 확률 | 80%로 나빠졌을 때 잡을 확률 |
|---|---|---|---|
| 10번 | 6번 이하 통과 | 1.3% | 12% |
| 20번 | 15번 이하 통과 | 4.3% | 37% |
| 70번 | 58번 이하 통과 | 4.4% | 77% |

10번 돌려서는 실제로 나빠진 경우의 12%만 잡힙니다. 지난 기록 없이 두 버전을 새로 돌려 비교하면 버전마다 약 157번이 드니, 사례별 통과율 기록은 쌓아 둘 가치가 있습니다.

평가 세트(채점 기준이 있는 사례 모음) 전체를 여러 번 돌리는 비용도 따져 봐야 합니다.

```
숫자는 모두 설명용 가정
  사례 200개, 사례 하나 = 에이전트 실행 한 번
  실행 한 번 = 입력 40,000토큰 × $1/1M + 출력 2,000토큰 × $5/1M = $0.05

  사례마다 1번:   200 ×  1 × $0.05 =  $10
  사례마다 5번:   200 ×  5 × $0.05 =  $50
  사례마다 70번:  200 × 70 × $0.05 = $700
```

> **제 해석**
>
> 프롬프트를 고칠 때마다 $700을 쓸 수는 없으니, 저는 반복 횟수를 사례마다 다르게 주겠습니다.
> - **세트 전체 통과율**은 사례 200개가 함께 표본이 되므로 한두 번 실행으로도 큰 하락은 보입니다. Anthropic의 [평가 통계 글](https://www.anthropic.com/research/statistical-approach-to-model-evals)도 문항마다 여러 번 샘플링해 평균을 쓰고, 같은 문항끼리 짝지어 비교하라고 권합니다.
> - **수십 번 반복**은 환불, 결제, 삭제처럼 틀리면 비싼 행동을 지키는 소수의 사례에만 씁니다.
> - **한 번의 실패**는 더 돌려 보라는 신호로만 씁니다. 몇 번 중 몇 번이면 회귀로 볼지는 결과를 보기 전에 정해 둡니다.
> - **비교 대상**은 출력 문자열 대신 고른 도구, 뽑아낸 필드, 끝난 뒤의 상태처럼 파싱한 결과(출력을 읽어 뽑아낸 값)로 둡니다.

재현이 꼭 필요한 곳에서는 저장한 출력을 씁니다. 응답을 처리하는 내 코드(파서, 후처리)는 녹화해 둔 응답을 재생해 시험하고, 사용자에게 나간 답은 다시 만들 수 없으니 출력 자체를 기록해 둡니다.

[하네스 엔지니어링 글](/blog/harness-engineering)에서 글로 쓴 지시보다 테스트 같은 확인 장치가 더 많은 일을 한다고 썼습니다. 다만 LLM 출력을 확인하는 장치는 통과율과 기준선을 함께 내놓아야 제 몫을 합니다.

## 아직 모르는 것

- **호스팅 API의 결정적 옵션.** 제가 찾아본 범위에서는 배치 불변 모드를 제공하는 호스팅 API를 보지 못했습니다. 나온다면 값과 지연이 얼마나 붙을지가 관건입니다.
- **다른 원인.** 원문도 GPU나 소프트웨어 버전이 바뀌면 결과가 달라질 수 있다고 적었습니다. 같은 이름의 API 모델도 서버 구성이 바뀌니, 오늘 잰 기준선의 유효기간을 알기 어렵습니다.
- **에이전트에서의 크기.** 수십 단계를 밟는 에이전트에서 첫 갈림이 최종 성공률을 얼마나 흔드는지 잰 자료는 보지 못했습니다.
